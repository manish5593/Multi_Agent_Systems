MUNDER DIFFLIN MULTI-AGENT SYSTEM: DESIGN NOTES
================================================

See workflow_diagram.png (or workflow_diagram.svg) for the architecture diagram.


1. OVERVIEW
-----------
The system handles free-text customer orders for Munder Difflin Paper Company.
For each request it works out which catalog items the customer wants, checks
whether they can be ready by the customer's deadline (from stock or a supplier
reorder), prices them with bulk discounts, records the sales, and replies to the
customer.

Framework: smolagents (ToolCallingAgent), model gpt-4o-mini via the Udacity
OpenAI-compatible proxy. The model can be changed with OPENAI_MODEL_ID in .env.

The system uses 4 agents, within the limit of 5.


2. AGENTS
---------
Orchestrator agent
  The entry point for every request. It extracts each requested item and its
  quantity (reams have already been converted to sheets by Python). It then
  delegates, in order, to the
  inventory, quoting and sales agents, and writes the customer reply: items
  sold with quantities, line totals, discounts and total, the delivery date,
  and the items it cannot supply. It always sells whatever is available rather
  than asking the customer to confirm. It is instructed never to substitute items,
  never to split a quantity across products, and never to reveal internal
  information (stock levels, costs, cash, suppliers, tool errors).

Inventory agent
  Tools: check_availability
  Passes each line of the customer's wording, verbatim, to check_availability,
  which picks the catalog item and checks whether the full quantity can be
  ready by the deadline. Items with no catalog match (e.g. balloons, A3 paper)
  are reported as not carried.

Quoting agent
  Tools: price_line_item, search_past_quotes
  Prices every available item using the bulk discount tiers and can look up
  similar historical quotes for context. It never invents prices.

Sales agent
  Tools: record_sale, check_cash_balance
  Records a sale for each quoted line. record_sale places any supplier reorder
  that is needed and records the sale at the quoted price.


3. TOOLS
--------
check_availability(description, quantity)                     [read-only]
  Takes the customer's wording for one item (e.g. "colorful cardstock") and
  matches it to a single catalog item in Python (see Catalog matching below).
  If current stock covers the quantity, the item is ready on the request date.
  Otherwise it plans a supplier reorder of (shortfall + minimum stock level),
  uses get_supplier_delivery_date for the lead time, and checks that the
  delivery arrives by the deadline and that the company can afford it. It
  writes nothing to the database, but records an approval for the matched
  item and quantity, and remembers which item the description matched.

Catalog matching (_best_catalog_match)
  Deterministic; no agent chooses between candidates.
  - A-series sizes the catalog does not stock (A3, A5) match nothing.
  - Aliases for wording unlike any catalog name ("printer paper" / "copy
    paper" -> Standard copy paper, "poster board" -> Large poster paper
    (24x36 inches)), unless the request names a stocked size such as A4.
  - Otherwise each item is scored by the share of its name words found in
    the description (plurals normalized), plus a bonus if it contains the
    description's main noun (its last word, e.g. "cardstock" in "colorful
    cardstock"), plus a little string similarity to break ties. Items must
    share at least one word with the description, so "cardboard" or
    "tickets" match nothing.
  On every item phrase in the 20 sample requests, the matcher picks the
  intended item (e.g. "colorful construction paper" -> Construction paper,
  "kraft paper envelopes" -> Envelopes, "A4 white printer paper" -> A4 paper).

price_line_item(item_name, quantity)
  List price (catalog unit price + 25% markup) minus the bulk discount:
    100+ units: 5%     500+ units: 10%     1000+ units: 15%
  Only an item and quantity approved by check_availability can be priced. It
  accepts the exact catalog name, the customer's description, or a near-miss
  name (e.g. "Washi tape", "A4 matte paper"), which is run through the same
  matcher; the approval check still applies.
  The catalog unit price is the supplier's price, used for restock costs and
  inventory value. After the largest discount, customers still pay
  1.25 x 0.85 = 1.0625 x cost, so every sale is profitable.

search_past_quotes(search_terms)
  Wraps search_quote_history to return up to 5 similar historical quotes.

record_sale(item_name, quantity)                              [writes]
  Accepts the catalog name, the customer's description, or a near-miss name
  (resolved as in price_line_item). Refuses unless
  check_availability approved this exact item and quantity
  earlier in the same request; each approval can be used once. It re-runs the
  availability plan, writes a stock_orders transaction if a reorder is needed,
  then writes a sales transaction priced with the same function as
  price_line_item, so the amount charged always matches the quote.

check_cash_balance()
  The company's cash balance on the request date (internal use).


4. DESIGN DECISIONS
-------------------
The guiding principle: the LLM decides WHAT to do; Python does every
calculation and every database write. Each rule below was added after a test
run showed the LLM getting it wrong.

a) Dates come from Python, not the LLM.
   call_multi_agent_system() stores the request date and parses the delivery
   deadline from the request text (e.g. "April 15, 2025"), defaulting to 14
   days after the request if none is found. Tools take no date arguments.
   Earlier versions let the LLM pass dates. It sometimes invented them (e.g.
   2023-11-24 for an April 2025 request), which caused false "insufficient
   funds" refusals (no cash exists before 2025), out-of-order sales that drove
   stock negative, and promised delivery dates after the customer's deadline.

b) Checking is separate from buying.
   An earlier version bought stock while checking availability. The agent
   checked several candidate items per request and bought all of them, so the
   company paid for stock nobody ordered. Now check_availability only checks,
   and stock is bought only inside record_sale for items actually being sold.

c) Sales must be approved.
   In one run the orchestrator, unable to find an exact match for "printer
   paper", asked for "similar items" and the agents sold 10 substitute
   products (about $36,000 for one order). record_sale now only accepts an item
   and quantity that check_availability approved in the same request, once.

d) One pricing function for quotes and sales.
   An earlier version let the sales agent pass the sale amount, and it
   recorded undiscounted totals (quoted $61.75, charged $65.00).

e) Reams are converted to sheets in Python, before any agent runs.
   call_multi_agent_system() rewrites "500 reams" as "250,000 sheets" in the
   request text. When an agent did the conversion, results were inconsistent:
   once 500 reams were restocked as 250,000 sheets but charged as 500 sheets,
   and later the orchestrator skipped the conversion entirely.

f) Tool calls run one at a time.
   smolagents runs an agent's tool calls in parallel threads by default.
   Parallel record_sale calls wrote to SQLite concurrently, and in one run the
   database file was corrupted ("database disk image is malformed").
   Every agent now uses max_tool_threads=1, and record_sale also holds a lock
   around its check-then-write.

g) Catalog matching happens once, in Python.
   Originally a find_catalog_items tool returned up to 5 candidates and each
   agent picked one. Agents picked inconsistently: "A3 paper" was sold as A4
   paper; "colorful construction paper" was approved as Colored paper even
   though the matcher ranked Construction paper first; and in another request
   the inventory agent approved Cardstock but the quoting agent re-matched the
   customer's wording and quoted Colored paper. Now check_availability does
   the matching itself, quoting and sales resolve the customer's wording to
   the item already matched, and only approved items can be priced or sold.

h) Inventory tracking for new items.
   When a catalog item that was not in the starting inventory is reordered, it
   is added to the inventory table so the financial report values it.

i) A 25% markup over the supplier price.
   Originally customers paid the catalog price minus a bulk discount, while
   restocking cost the full catalog price, so every discounted sale of
   restocked stock lost money (one run's 250,000-sheet order cost $10,004 to
   restock and sold for $8,500). Any markup above 17.6% keeps the 15% tier
   profitable; 25% leaves a margin of at least 6.25%. It is MARKUP_RATE in
   project_starter.py.

j) Starter code fixes.
   run_test_scenarios() called init_database() without its required argument
   and printed an undefined `response`; both are fixed. One failed request is
   caught and logged so the run continues.

6. KNOWN LIMITATIONS AND POSSIBLE IMPROVEMENTS
----------------------------------------------
- The matcher is a word-overlap heuristic tuned on the sample requests.
  Wording unlike any catalog name (e.g. a brand name) needs an alias, and
  attributes other than the main noun and paper size, such as "recycled" in
  "recycled cardstock", are ignored. An embedding-based match would be more
  general.
- If the LLM paraphrases a description instead of copying it, the matcher
  sees the paraphrase.
- If two requested lines match the same catalog item, the second check
  replaces the first approval.
- If the sales agent tries a different item than the one approved, the
  guard blocks it; the agent usually retries with the approved item, but in
  one earlier run it did not and an available item went unsold.
- The transaction IDs returned by the starter's create_transaction are
  unreliable (it reads last_insert_rowid() on whichever pooled connection it
  gets), so tool messages sometimes show repeated IDs. The stored rows are
  correct.
- Reordered stock counts as available from the order date, not the delivery
  date. This only matters if two requests for the same item arrive while a
  supplier delivery is still in transit.
- Units other than reams (packets, boxes) are treated as single units.
- Some behavior still depends on the LLM following instructions, such as
  always selling available items and not offering alternatives. The tool
  guards prevent wrong sales, but cannot force a sale the agent skips.
- Replies sometimes say "insufficient stock" or name the supplier's delivery
  date. They give no numbers, but a stricter reply template could remove this.


7. HOW TO RUN
-------------
  python3.11 -m venv .venv && source .venv/bin/activate
  pip install -r requirements.txt
  echo "UDACITY_OPENAI_API_KEY=<your key>" > .env
  python project_starter.py

This creates munder_difflin.db, processes the 20 sample requests, prints a
final financial report, and writes test_results.csv. A full run takes about
15-25 minutes.
